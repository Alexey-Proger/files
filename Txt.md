# ПЗ-01. Введение в инженерию ПО. Жизненный цикл и модели разработки


## 1. Теория: программа — это продукт

На курсе алгоритмизации вы решали задачи: «дано N, найти X». Решение = **алгоритм**, который где-то "работает" в тетрадке или в одной отладочной программе.

В промышленной разработке программа — это **продукт**, который:
- кто-то **использует** (пользователь, заказчик);
- кто-то **сопровождает** (исправляет ошибки, добавляет функции — часто другие люди);
- должен **не падать** при дурацком вводе;
- **меняется** со временем.

> Запомните формулу курса: **«решил» — это 20% работы.** Остальные 80% — структура кода, устойчивость, тесты, контроль версий, документация. Весь семестр мы будем учиться делать эти 80%.

## 2. Теория: жизненный цикл ПО (ЖЦ)

**Жизненный цикл ПО** — последовательность этапов, которые проходит программа от идеи до вывода из эксплуатации.

Классические этапы:

| Этап | Вопрос, на который отвечает | Результат |
|---|---|---|
| Анализ требований | Что должна делать система? | Техническое задание, список требований |
| Проектирование | Как она будет устроена? | Архитектура, схема модулей, структура БД |
| Реализация (кодирование) | Пишем код | Работающие модули |
| Тестирование | Работает ли правильно? | Отчёт о тестировании, исправленные дефекты |
| Внедрение | Как отдать пользователю? | Установка, обучение, документация |
| Сопровождение | Что делать, когда появились баги и новые хотелки? | Исправления, новые версии |

На практике эти этапы **не всегда идут строго по порядку** — отсюда разные модели.

## 3. Теория: модели процесса разработки

### 3.1. Каскадная («водопад», Waterfall)

```
Требования → Проектирование → Реализация → Тестирование → Внедрение
```

- Каждый этап полностью завершается до начала следующего.
- **Плюсы:** простота, понятная документация на каждом этапе.
- **Минусы:** ошибку в требованиях замечают только на тестировании (а это конец проекта); заказчик видит результат в самом конце.
- **Где применяется:** проекты с жёстко фиксированными требованиями (например, госзаказ, «калькулятор по ГОСТ»).

### 3.2. V-модель

- Каждому этапу разработки соответствует этап тестирования того же уровня (анализ требований ↔ приёмочные тесты, проектирование ↔ интеграционные тесты, кодирование ↔ модульные тесты).
- **Идея:** тесты планируются заранее, вместе с разработкой, а не «потом».
- **Где применяется:** инженерные системы, где важна безопасность (авиация, медицина).

### 3.3. Итеративные модели (инкрементальная, спиральная)

- Система собирается **маленькими кусками — итерациями**. Каждая итерация: взяли небольшое требование → спроектировали → написали → протестировали → показали заказчику → получили обратную связь → следующая итерация.
- **Плюсы:** работающий продукт появляется рано; ошибки видны сразу; требования можно уточнять по ходу.
- **Минусы:** нужна дисциплина (не «допишу потом»), сложнее планировать точные сроки.

### 3.4. Гибкие методологии (Agile: Scrum, Kanban)

- Философия Agile: люди и взаимодействие важнее процессов; работающий продукт важнее документации; реакция на изменения важнее следования плану.
- **Scrum:** короткие циклы — спринты (1–4 недели), роли (владелец продукта, Scrum-мастер, команда), доска задач (бэклог, в работе, готово).
- **Kanban:** непрерывный поток задач, лимит одновременной работы.
- **Где применяется:** веб-разработка, стартапы, всё, где требования меняются — то есть почти всё современное.

> **Вывод для всего курса.** Мы будем работать **итеративно**: маленькими шагами, каждый шаг доводим до работающего состояния и коммитим. Это и есть современный способ разработки, и он же — самый удобный для обучения.

Установите и проверьте (делаем вместе, по шагам):

| # | Шаг | Проверка |

## 5. Задания (выполняются на занятии, сдаются по чек-листу)

**Задание 1. «Моя программа как продукт» (20 мин)**
Возьмите любую решённую вами на алгоритмизации задачу (например, «найти сумму цифр числа»). Письменно (в Markdown-файле `product.md` в своей папке) ответьте на 4 вопроса:
1. Кто «пользователь» этой программы и что он вводит?
2. Что произойдёт, если пользователь введёт не число, а текст? (Напишите, что *должно* произойти.)
3. Какие 2 новых требования вы бы добавили, если бы программа была продуктом?
4. Какой этап ЖЦ у вашей задачи был пропущен на алгоритмизации и к чему это привело?

**Задание 2. Выбор модели ЖЦ (20 мин)**
Для трёх сценариев выберите модель разработки и обоснуйте одним предложением:
1. Расчётная программа для начисления зарплаты по утверждённому законом алгоритму.
2. Мобильное приложение для доставки еды, рынок которого меняется каждый квартал.
3. Система управления полётом дрона, где ошибка стоит жизни.

Ответ запишите в тот же файл `product.md` (раздел «Модели ЖЦ»).

**Задание 3. Окружение готово (20 мин)**
Выполните шаги из раздела 4 и сохраните вывод команд в файл `setup.txt`:
```
python --version

```
Скопируйте вывод в `setup.txt`.
